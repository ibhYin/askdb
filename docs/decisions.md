# 设计决策记录（ADR）

每条都按"背景 → 选择 → 证据 → 放弃的替代方案"写。
面试时被问"为什么这么做"，答案就在这里。

---

## 1. 不用 LangChain，手写循环

**背景**：任务只有"生成 SQL → 执行 → 把结果/报错回灌 → 再生成"。

**选择**：`askdb/agent.py` 里约 150 行手写循环。

**证据**：循环里的每一步都要精确控制——第几轮、回灌什么文本、什么时候判定收敛。
框架的抽象层反而让"上下文里到底多了什么"变得不直观。

**放弃**：LangGraph 的 checkpointer 在多会话/中断恢复时确实好用。
真要做多轮对话和断点续跑，会重新评估。

---

## 2. 评测器先用 gold SQL 自检，再采信分数

**背景**：第一次跑多库评测，自检 95%，不是 100%。

**选择**：`--self-check` 用 gold SQL 冒充模型输出，必须 100% 才算尺子准。

**证据**：自检抓到三个真 bug——
1. 带 evidence 的题 mock 匹配不上（匹配键用了 question 原文）
2. 评测沿用了 agent 的 200 行上限，929 行的题被判"答错"
3. gold 查询 10s 超时，bird-119 直接打断整轮评测

**放弃**：直接相信第一次的 95%——那会把 5 个点的评测器 bug 当成模型能力。

---

## 3. schema 检索用 IDF 词法匹配，不用 embedding

**背景**：大库有 8~14 张表、上百列，全塞进 prompt 既贵又吵。

**选择**：`schema_index.py`，IDF 加权词命中 + 前缀匹配 + 外键邻居。

**证据**：
- 表召回 top_k=6 时 96.7%，完全命中 91.7%（离线可测，不烧 API）
- 端到端 EX 62.7% → 66.7%，P95 从 67s 降到 37s
- 前缀匹配是必需的：`SAT` 匹配不到 `satscores`（全小写复合表名没有分词点）

**放弃**：embedding 检索。多一次网络调用、每次评测都要重算、
还引入一个模型作为变量。**先用最便宜的方案拿到数据，再决定要不要升级。**

---

## 4. 邻居扩展选"高召回"而不是"高压缩"

**背景**：选了 top_k 张表后，要不要把外键邻居也带上？

**选择**：带上全部外键邻居（压缩率从 34% 降到 24%）。

**证据**：只补"自身也命中"的邻居，表召回从 96.7% 掉到 93.3%。

**放弃**：更高压缩率。表没进 prompt，模型再强也写不出来；
BIRD 的库不大，多几张表的 token 代价小于漏表的正确率代价。

---

## 5. SQL 执行做双重只读

**选择**：连接 `mode=ro`（物理只读）+ authorizer 白名单（逻辑只读），再叠加超时与行数上限。

**证据**：单测里 `DELETE/DROP/ATTACH/PRAGMA/load_extension` 全部 `not authorized`，
执行后 COUNT 不变；无限递归 CTE 在 50ms 被中断。

**放弃**：只靠 SQL 字符串正则过滤——模型能构造出绕过正则的写法。

---

## 6. 报告永不覆盖

**背景**：同一秒内跑两次，文件名撞了。

**选择**：run_id 带微秒与数据集名，重名自动加后缀。

**证据**：加了一条测试专门守这个。覆盖一次就等于丢一次基线，比较从此失去意义。

---

## 7. 长任务必须打进度

**背景**：第一次跑全量 496 题，21 分钟没有任何输出。判断不了是死是活，只能杀掉重跑。

**选择**：`run_eval` 每 25 题打印一行，启动时打印题目数与模型名。

**教训**：无法观察的长时间运行，等于不可靠。这跟"没有指标的项目等于没做完"是同一件事。

---

## 8. 坏题隔离而不是降低标准

**背景**：BIRD 500 题里有 4 道 gold SQL 跑不通或结果为空。

**选择**：`scripts/check_bird.py` 体检 → `data/bird/invalid_ids.json` → 加载时跳过。

**证据**：`bird-16/37/44` 结果为空，`bird-40` 超时。
这些题的 gold 本身有问题，算进分母等于给模型扣分。

**放弃**：让它们算错题。那会把数据集的缺陷记到模型头上。

---

## 9. 只有全量结果算结论，抽样只能当方向

**背景**：150 题抽样上，schema 检索看起来值 +4.0pt（62.7% → 66.7%）；
提示词 v2 只值 +1.3pt，我据此把默认提示词改回了 v1。

**后来**：全量 496 题跑完，两个结论都被推翻——
检索是 **+0.0pt**（286 对 286），而 v2 是 **+4.2pt**（286 → 307）。

**原因**：
- 抽样集本身更容易（62.7% vs 全量 57.7%），难度分布不同
- 150 题上 6 道题的波动就是 4 个点，看起来像趋势；到 496 题就消失了

**现在的规则**：
- 抽样（150 题以内）只用来判断"方向对不对、有没有明显 bug"
- **任何要写进 README 或简历的数字，必须来自全量**
- 改默认配置之前，先跑全量

**代价**：全量一轮 496 题、并发 3，约 70 分钟。这个成本必须付。

---

## 10. 在评测集上调参，就不能只用评测集报成绩

**背景**：最终配置（v2 提示词 + schema 检索 + 取值样例）是在 496 题上
逐组试出来、又在同一批题上报的 65.1%。

**问题**：这是标准的"在 dev 上调参，在 dev 上报分"。官方 61.0% 是固定 prompt 跑出来的，
拿 65.1% 去说"超过官方"，等于拿调过的成绩比没调过的。

**现在的做法**：
- 内部只声称"同一套题上配置演进带来 +7.4pt"，这是有对照、可复现的
- 对外明确写"含调参成分，与官方同量级，不宣称超越"
- 下一步：在 BIRD test split 或另一批未参与调参的题上复测一次，才敢写"泛化"

**这个偏差不是小事**：如果面试官问"你的 65.1% 有没有过拟合到这套题"，
答不上来就会让前面所有数字打折；能主动指出来，反而加分。
